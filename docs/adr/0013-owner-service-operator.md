# ADR 0013: Class-based owner-service operator

- Status: accepted
- Date: 2026-08-14

## Context

Root-policy actions and declarative deployments remain the correct product API
for Hub-driven operations. They fail closed, take no caller command, and cannot
grow by adding one sudoers line per button.

That model is too expensive for the remaining operator workflow: a person or
their coding agent already on the Tailnet as `lodge-admin` needs to maintain
non-root services that the host owner already runs, such as a user-owned proxy.
Each new incident previously required a unique root console script. That is
safe, and it does not scale.

SSH as those service-owner accounts is the wrong expansion. On cloud images the
owner account often has `NOPASSWD: ALL`. Tailnet SSH as `ecs-user` would restore
a root shell. Arbitrary `lodge-admin` sudo would do the same.

## Decision

Add one standing capability class: maintain **opt-in non-root service-owner
accounts**.

`/etc/lodge-agent/operator.json` is a regular, non-symlink, root-owned `0600`
file. It lists local usernames only. A missing or empty policy fails closed.
Denied names include `root`, `lodge`, `lodge-admin`, and other system accounts.

`lodge-admin` may invoke two exact sudo helpers generated by
`lodge-agent --print-admin-sudoers`:

- `--list-operator`
- `--execute-operator`

Both accept no extra argv. The write helper reads one bounded JSON object from
stdin and supports only:

- `read-file` / `write-file` / `list-dir` under that user's home, after
  rejecting absolute paths, `..`, symlink escape, and credential locations
  (`.ssh`, `.gnupg`, `.aws`, and similar);
- `write-file` only for an existing regular file owned by that user, with a
  size bound, optional SHA-256 compare-and-swap, and a root-only backup;
- `unit-status` / `unit-restart` only when `systemctl show -p User` equals the
  allowed user and the unit is not a denied system service.

The network-facing `lodge` service account does **not** receive this sudo.
Agent HTTP still cannot accept a path, command, or file body. Authorization for
this class is the existing Tailnet `lodge-admin` identity, not a Hub browser
shell.

Adding a new service under an already-listed owner requires no new sudoers
rule. Adding a new owner still requires an explicit root policy edit.

## Consequences

- One Agent upgrade plus an owner list replaces per-incident console scripts
  for user-owned configs and their systemd units.
- This is not a remote shell, package manager, or root file editor.
- Compromising `lodge-admin` on the Tailnet can now rewrite opted-in owner
  service config and restart those units. That is an accepted operator-plane
  expansion; it is still narrower than owner-account SSH or `NOPASSWD: ALL`.
- Hub-projected operator actions remain future work and must reuse this helper,
  not invent a second path.
